# Unified static visual GPU inspection

This path renders the common static visual artifact through `eqoxide_renderer::static_visual`, independently of the legacy zone loader and the game loop. The bounded CPU decoder supplies server-axis meshes, material semantics, exact PNG payloads and instance matrices. `PreparedStaticVisual::decode` creates private preparation data; `GpuStaticVisual::upload` builds a complete resource set. For the older display profiles, the caller owns its render pass, color/depth targets and submission. The opt-in HDR profile below owns its intermediate color/depth targets and encodes two passes into the caller's command encoder. Drawing fails until camera preparation succeeds; failed camera preparation invalidates prior prepared state rather than permitting a stale camera draw.

This inspector supports legacy/explicit unlit materials and a bounded standard metallic/roughness factor profile selected by `pbr-metallic-roughness-factors-v1`. The prepared scene reports `pbr-factors-reference-light-v1` when it contains PBR materials, otherwise `unlit-inspection`. This is reference illumination for material inspection, not full production PBR. Production zone resources, shaders, online reader advertisements, collision/navigation and lifecycle are unchanged. The isolated interactive preview is documented in `docs/unified-static-preview.md`.

Lit OPAQUE/MASK materials use one directional light with GGX distribution, separable Smith visibility and Schlick Fresnel, plus approximate constant diffuse/specular ambient fill. The ambient term is not filtered cubemap image-based lighting or global illumination. The shader applies an evaluation floor of `0.045` to roughness without changing the decoded material, then exposure and per-fragment Reinhard display mapping. Explicit and legacy unlit bypass illumination and that display mapping. Lit BLEND remains refused by this older scalar-only profile. There is no environment map, shadow, fog, normal map, occlusion map or emissive input in either current profile.

## Opt-in HDR transparency

Artifacts requiring `pbr-metallic-roughness-blend-v1` select `pbr-hdr-blend-reference-light-v1`. `GpuStaticVisual::upload` explicitly refuses them; callers use `GpuHdrStaticVisual::upload`, `resize`, `prepare_camera` and `encode`. The standalone example and isolated preview select this route from the typed prepared profile. The older display-profile API and appearance remain unchanged.

The new profile renders linear radiance into an `Rgba16Float` target with `Depth32Float` depth, then applies exposure and Reinhard mapping once after composition. Lit materials use the same reference BRDF and lighting. Explicit unlit materials bypass illumination, supplying base-color RGB as radiance, but share the new profile's common exposure and display mapping. This differs intentionally from older unlit display behavior. MASK survivors and OPAQUE fragments use coverage one even when their source alpha is zero; BLEND uses the full texture/factor/vertex alpha product. Solid draws write depth, transparent draws test depth without writing it. Transparent radiance is premultiplied and composed with `One / OneMinusSrcAlpha`. The existing stable primitive-instance sorting limitations apply.

This is a finite half-float contract: f32 shading clamps each straight RGB channel to `[0,65504]` **before** premultiplication and storage. In-range composition is linear, subject to half-float and GPU arithmetic precision. Extreme out-of-range radiance is clipped, so a very bright low-alpha layer may be dimmer than unbounded HDR arithmetic would predict; later attenuation cannot recover clipped energy. No exact all-radiance or hardware-wide numerical guarantee is claimed. The baseline requires no optional float32 blending feature and performs no per-frame overflow readback. The final display pass uses a texture load, a single exposure/Reinhard operation and the sRGB output attachment. Its output is opaque alpha one over a configured opaque linear-radiance background; it is not transparent-canvas export, native water animation, refraction or order-independent transparency.

HDR upload accepts explicit `UploadLimits` again, including per-image, draw and triangle limits. `HdrFrameLimits` defaults to dimension 16384, further bounded by the actual device limit, and 128 MiB of retained frame color/depth payload. Checked frame payload is `12 * width * height`; the display uniform adds 16 bytes. Scene, display uniform and frame targets must together fit the upload aggregate budget (default 512 MiB) before allocation. Caller output/capture targets and driver allocations are excluded. `HdrGpuStats` reports scene, postprocess, frame and total committed payloads plus dimensions. These are retained logical payloads, not process RSS, peak resize memory or driver usage.

A repeated accepted extent reuses its targets. Resize validates dimensions and budgets before creating a replacement; old and new allocations can transiently coexist. Failed resize invalidates target readiness while retaining the last owned allocation; a successful resize recovers. Camera failure invalidates drawing until successful preparation. `encode` requires both target and camera readiness. The caller must provide an output view of the upload-time format and current accepted extent, and owns submission and device-error handling. Successful encoding does not certify GPU execution or frame visibility. Device creation/upload/target errors are returned with scoped dependency-panic isolation where unwinding is available.

`GpuStaticVisual::upload` uses `ReferenceLighting::default()` for both offline rendering and preview. Its direction toward the light is `[0.4,-0.6,1.0]` (normalized on upload), directional RGB radiance `[3.0,2.8,2.6]`, ambient RGB radiance `[0.08,0.10,0.14]` and exposure `1`. `upload_with_lighting` accepts another immutable reference setup: direction must be finite and nonzero, each radiance channel finite in `[0,64]`, and exposure finite in `(0,16]`. Invalid lighting fails before allocation. Lighting belongs to the shared renderer rather than a source-family material or baked light texture.

The shader first computes texture RGBA times material RGBA times interpolated vertex RGBA; lit materials use the RGB product as their base color. Texture RGB is interpreted as sRGB and converted to linear; material factors, vertex colors and alpha remain linear. Opaque ignores alpha for coverage and writes alpha one. Mask discards only below the actual material cutoff using the full alpha product; surviving fragments write alpha one. Blend uses straight alpha, depth tests against solid surfaces and does not write depth. Single-sided materials cull back faces; double-sided materials show both faces. Geometry and instance matrices use decoded server axes directly, without another source-axis conversion.

Meshes share position/primary-UV/normal buffers and instance records. Validated unit normals are uploaded and rotated by each positive-uniform instance transform; normalizing its columns first avoids overflow from a large scale. PBR normals are normalized after interpolation and flipped on double-sided backfaces. A zero interpolated normal uses server up Z; a zero eye-to-fragment vector uses the validated camera direction, and a zero light/view half vector uses the surface normal. Colored primitives have separate full RGBA streams; uncolored primitives use white. Images are uploaded once even when multiple texture indices alias them. Names and generator metadata select no behavior; a visual mesh named `__collision__` remains visual.

PNG input is converted to float32 without reducing 16-bit samples to eight bits. Texture RGB receives the sRGB transfer conversion; alpha does not. GPU images use `Rgba32Float`, a nonfilterable binding and explicit repeat/bilinear sampling through `textureLoad`, so optional float-filtering device features are unnecessary. UVs wrap before integer addressing, including negative and large finite coordinates. Inspection uses the base image level without mipmaps or anisotropic filtering. Final PNG output uses an eight-bit sRGB target; precision-sensitive alpha decisions occur before that output encoding.

Float texture payloads cost four times as much as RGBA8 and twice as much as RGBA16. These are GPU payload limits, not bounds on peak CPU preparation memory. PNG decoding and conversion can transiently retain source pixels and a float image; preparation transforms that owned float buffer in place instead of allocating another full float copy. Unreferenced declared images remain validated, prepared, counted and uploaded under the same limits. Default upload limits are 512 MiB across buffer/texture payloads, 64 MiB per float image, 1,000,000 draw commands and 20,000,000 triangle instances. The checked primitive-instance blend-command product, total indexed triangles across all instances (including solid instancing), and buffer/texture payloads are bounded before per-instance PBR coordinate validation, command allocation or texture conversion. PBR material classification is computed once per mesh, so instances do not repeatedly scan primitive materials. Geometry/color/index/instance buffers, material/camera/light uniforms and fallback resources contribute to accounting. Shared position/UV/normal records cost 32 bytes per vertex, material uniforms 48 bytes each, camera data 96 bytes and reference lighting 64 bytes. Device buffer and texture limits are checked before allocation, including three vertex buffers, eight vertex attributes, a 64-byte supported vertex stride, a 96-byte uniform binding, three uniform bindings per shader stage, two bind groups and one sampled texture. These payload/work budgets do not bound total process memory or driver overhead; callers can provide explicit overrides. Decoder limits apply separately before GPU preparation.

Opaque and masked surfaces retain full instancing. Camera matrices follow the existing right-handed convention: camera-forward is negative view-space Z, with conventional WebGPU depth increasing from near zero to far one. All camera preparation checks finiteness and multiplication overflow; callers are responsible for supplying this convention. PBR additionally requires an affine invertible view, a finite derived eye and nonzero view direction, and an ordinary perspective or orthographic projection shape. Perspective matrices must have zero X/Y translation in their fourth column so view rays meet the derived eye; orthographic matrices must have zero X/Y components in their third column so view rays remain parallel to view Z. Each view-projection coefficient and eye-coordinate magnitude is limited to `1e12`. For every mesh containing a PBR primitive, each placed vertex's sum of absolute affine intermediate contributions per coordinate is also limited to `1e12`, including unreferenced vertices. These are explicit reference-renderer bounds rather than relaxed CPU scene limits. For scenes containing PBR materials, GPU positions use world axes relative to the derived camera eye. Instance translations subtract that origin in f64. The matching view-projection first cancels the origin in view space as `view * translation(eye)` in f64, then applies the projection before packing as f32. Perspective lighting uses the relative eye at zero; orthographic lighting retains its parallel world-space view direction. This preserves local geometry under large instance/camera translations without recovering precision already lost in the original f32 matrices or vertex positions. Original matrices remain authoritative for world bounds and CPU blend depth. A changed eye causes a bounded upload of all instance transform records; preparing the same eye reuses those records. The 64-byte instance records, 96-byte camera uniform and reported GPU payload sizes stay the same. All camera checks, relative-payload validation and blend ordering finish before queue writes, and a failed preparation invalidates drawing until a later successful preparation. Legacy/unlit cameras retain their prior finite-only matrix checks and zero origin. Blend draws use stable camera-depth order per primitive-instance, with centers derived from the primitive's referenced vertices. This common sorting policy does not solve intersecting transparent surfaces, transparent cycles or ordering within a primitive. Those limitations must be addressed separately before declaring broader production fidelity.

Display inspection requires `Rgba8UnormSrgb` or `Bgra8UnormSrgb` output; linear UNORM targets are rejected. Shader math and blending remain linear, and the attachment encodes RGB for display. `Rgba32Float` unfiltered texture binding is part of the baseline device format contract; no optional float-filtering feature is requested. Hardware or validation failures still return an error, and finite adapter testing does not certify every GPU. The interactive surface must support capture; BGRA readback converts channels before PNG encoding.

The standalone example requires a working GPU adapter and returns a nonzero error if the artifact, device, upload or readback fails:

```sh
cargo run -p eqoxide-renderer --example static_visual_render -- INPUT.glb OUTPUT.png
```

It bounds the input read, frames the validated server-world bounds, renders a 512-by-512 image against an opaque dark background, and writes an actual PNG from GPU readback. The opaque background avoids interpreting a premultiplied transparent framebuffer as a straight-alpha PNG. It prints inspection statistics, separate HDR payloads when selected, CPU encoding time and submit-plus-readback wall time (not isolated GPU time or game FPS), adapter/output details, the actual prepared `render_profile` and `lighting_applied` flag; `lighting=reference` selects the PBR reference path and `lighting=unlit` selects the unlit path. The flag describes the prepared material profile, not proof that a lit surface covers a pixel. The example does not start a game account, network task or asset-server session.

For a native-free input, use `crates/eqoxide-assets/tests/fixtures/static-visual-v1.glb`. The fixture has one mesh shared by two transformed instances; its server bounds are `[-3,-7,2]` to `[16.44179,13,6.5]`. Actual GPU acceptance must separately verify material factors, full vertex RGBA, alpha modes/cutoff, sidedness, coordinate placement and precision. Shader parsing alone does not prove rendering correctness.
